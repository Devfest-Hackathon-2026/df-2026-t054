# 問題を消せるのは，作った人が，まだ自分しか参加していないときだけにする（2026-11-08）

- 決めたこと:
  - ルール（`firebase/firestore.rules`）で `problems/{problemId}` の削除を「作った人（`ownerUid`）で，`memberUids == [自分]`」のときだけ許す．画面（`web/src/ProblemDetail.tsx`）も同じ条件のときだけ「この問題を削除」ボタンを出し，`window.confirm` で元に戻せないことを確かめてから消す
  - ブラウザは問題のドキュメントだけを消す．投稿・ステップなどのサブコレクションと Storage の `problems/{problemId}/` の下のファイルは，`server/` の `deleteProblemData`（`onDocumentDeleted('problems/{problemId}')`）が Admin SDK の `recursiveDelete` と `bucket.deleteFiles({ prefix })` で消す
  - ブラウザからは `deleteDoc` ではなくトランザクション（読んで条件を確かめてから `delete`）で消す
- 理由:
  - 誤って作った問題を片付けたい，という要望に対して，ほかの人の解法を巻き込まない範囲に絞った（人間と相談済み）．参加者が自分1人なら，消えるのは自分のデータだけ
  - ルールの判定は削除の時点のドキュメントで行われるので，ボタンを押す直前にだれかが参加していても，その人の解法は消えない
  - Firestore はドキュメントを消してもサブコレクションを消さない．`steps` はルールで書けない（サーバーだけ）ので，ブラウザからは消し切れない．サーバーのトリガーなら Admin SDK でまとめて消せる
  - `deleteDoc` はサーバーの返事を待たずに手元のキャッシュから問題を消すので，ルールで拒否されたとき画面が「問題が見つかりません」になってから元に戻り，エラーの表示も消えてしまう．トランザクションはサーバーで確定してから反映されるので，拒否されたときは詳細ページのままエラーを出せる
  - 削除と同時に処理中だったステップ化・式変形の確認は，結果を書く前に投稿・ステップがあるかを確かめるので，消したあとに結果を書き戻さない．消すのとほぼ同時に投稿していたときだけ `processing` のステップが残りうるが，問題が無いので画面からは届かず，害はないので対処しない
- デプロイの順番: ルールだけを先に出すと，問題のドキュメントは消えるが `deleteProblemData` がまだ無いので，投稿・ステップ・Storage のファイルが残る（あとから Functions を出しても，過去の削除は拾わない）．`--only firestore:rules,functions` で同時に出すか，Functions を先に出す（PR #77 のレビューで指摘）
- 捨てた案とその理由:
  - 締め切り（全員の提出）より前ならいつでも消せる: ほかの人の投稿まで消えてしまう
  - 一覧から隠すだけ（取り消せる）: 削除ではなく，データが残り続ける．要望は「消したい」だった
  - サブコレクションもブラウザから消す: `steps` はルールで書けず，Storage も上書き・削除を禁止しているので，ルールを大きく緩めることになる
