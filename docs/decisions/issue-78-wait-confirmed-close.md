# 締め切りは，サーバーで確定した問題の状態で判断する（2026-11-08）

- 決めたこと:
  - `web/src/useProblem.ts` の `onSnapshot` に `{ includeMetadataChanges: true }` を付け，`snap.metadata.hasPendingWrites` が false のスナップショット（サーバーで確定した状態）を `confirmed` として別に持つ．締め切り（`closed`）は `isAllSubmitted(confirmed)` で決め，`ProblemDetail` に渡す
  - 自分の書き込みが届く前のローカルの状態（`problem`）は，「提出済み」「提出 N 人」などの表示にはそのまま使う（押した直後に表示が変わるのは今と同じ）
  - ルール（共有の契約）は変えていない
- 理由:
  - 最後の1人が提出すると，ローカルの書き込みだけで `isAllSubmitted` が true になり，サーバーがまだ締め切っていないうちに質問・比較・ほかの人の投稿の読み込みが始まって，ルールの `canSeeOthers` に拒否されていた．`onSnapshot` はエラーで止まるので再読み込みまで直らない
  - 書き込みが確定（`hasPendingWrites` が false）した時点ではサーバーに反映されているので，その後に始める読み込みはルールで通る
  - `includeMetadataChanges` を付けないと，データが変わらず `hasPendingWrites` だけが変わったときに通知されず，締め切りに切り替わらない
  - 「締め切りから戻る」方向（確定済みの締め切りのあとに自分の書き込みが保留になる）でも `confirmed` は前の確定状態のままなので，節が一瞬消えることはない
- 捨てた案とその理由:
  - `ProblemDetail` で `isAllSubmitted(problem) && !hasPendingWrites` とする: 締め切りのあとに何か書き込みが保留になると，そのあいだ節が消える．確定した状態を持つ方が素直
  - 保留中のスナップショットを捨てて，確定した状態だけを返す: 押した直後の「提出済み」表示がサーバーの応答まで遅れる
  - 読み込み側（`useThreads` など）で `permission-denied` のときに少し待って読み直す: 読み込み側すべてに手を入れることになり，原因（判断が早すぎる）を残したまま症状だけ消すことになる
  - `submitPost` の Promise が解決するまで締め切りと見なさない: 提出の操作（`SubmitControls`）と表示（`ProblemDetail`）のあいだで状態を受け渡す必要があり，別のタブ・端末からの書き込みには効かない
- 承知のうえの弱さ:
  - オフラインで提出すると，つながるまで締め切りにならない（サーバーがまだ締め切っていないので，それで正しい）
  - 最後の1人が提出してからサーバーが受け取るまでのごく短いあいだ，表示は「提出済み」で `closed` は false なので「提出を取り消す」が出ている．押してもルール（`!allSubmitted(...)`）で拒否されてエラーが出るだけで，データは壊れないので，そのままにした（PR #84 のレビュー）
- テスト・確認:
  - `cd web && npm run lint && npm run build`
  - エミュレータ（Auth・Firestore）で，テスト用アカウント2つ（A は提出済み，B は下書きでステップ done を手で置いた）を使い，B が最後に提出 → 再読み込みなしで質問・分岐点の図・ほかの参加者の投稿とステップがエラーなく出ることを確かめた．同じ手順を直す前のコードで行うと「質問を読み込めませんでした: evaluation error at L185…」が出ることも確かめた
  - 全員がそろう前の提出・取り消しで，表示（提出済み・下書き・提出 N 人）が前と同じことを確かめた
  - レビュー（PR #84）で，Firestore エミュレータのスクリプトで同じ判断の仕方を10回ずつ試してもらった．直す前の判断では質問のスレッド・ほかの人の投稿が毎回 `permission-denied`，この判断の仕方では質問のスレッド・ほかの人の投稿とステップ・比較・問いかけへの理由のどれも10回とも読めた（`useProblem.ts` そのものではなく，スクリプトで同じ判断を書き直したもの）
