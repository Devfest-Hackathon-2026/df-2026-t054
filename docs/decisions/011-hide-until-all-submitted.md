# 投稿＝提出とし，参加者全員が提出するまで他人の投稿・ステップ・ファイルをルールで隠す．そろったら締め切る（2026-11-08）

- 決めたこと:
  - 提出: 投稿を書くこと自体を提出とする．初めて投稿するときは，同じバッチで自分の uid を `problems/{problemId}.submittedUids` の末尾に足す（`web/src/posts.ts` の `writePost`）
    - ルールは両方向で確かめる: 投稿は「書いたあと自分が `submittedUids` に入っている」（`getAfter`），`submittedUids` への追加は「書いたあと自分の投稿がある」（`existsAfter`）．別々に書くとどちらも拒否される
  - 「全員が提出した」＝ `memberUids.size() >= 2 && submittedUids.size() == memberUids.size()`（`firebase/firestore.rules`・`firebase/storage.rules`・`web/src/problems.ts` の3か所で揃える）
  - 公開: 全員が提出したら，参加者は他の人の `posts/{uid}`・`steps/{uid}`（`get` と `list`）と Storage のファイル（`get`）を読める．それまでは本人だけ．参加していない人はいつでも読めない
  - 締め切り: 全員が提出したら，problem の更新（参加・提出）・投稿の出し直し・Storage への新しいアップロードをすべて拒否する．提出前（全員そろう前）の出し直しは許す
  - 画面: 詳細に「参加者 n 人・提出 m 人」と公開の状態を出し，締め切り後は「出し直す」と招待リンクからの「参加する」を出さない．他の人の投稿を並べる画面は #16 以降で作る
  - ルールのテスト: `firebase/test/rules.test.ts`（`@firebase/rules-unit-testing` ＋ Node 標準の `node:test`）．`firebase/` で `npm install` → `npm test`（`emulators:exec` で Firestore・Storage のエミュレータを立てて流す．プロジェクト ID は `demo-gdgoc` で本番に触れない）
  - データ構造（共有の契約）は変えていない．007 で用意した `submittedUids` を使い始め，problem の更新で許す項目に `submittedUids` を足しただけ
- 理由:
  - 007 の残った論点「全員が提出したあとに新しい人が参加すると非公開に戻る」は，締め切ってしまえば起きない．作った人が締め切る操作を足すより，項目もボタンも増えない
  - 参加者が1人のうちを「全員」と見なさないのは，作った人が招待リンクを配る前に自分の解法を出すと，その瞬間に締め切られて誰も参加できなくなるため
  - 提出を投稿と別のボタンにしないのは，MVP では「下書き」が要らず，1人1投稿（008）なので「投稿がある＝提出した」で足りるため
  - 公開後に出し直しを止めるのは，他の人の解法を見てから自分の解法を書き換えられると「別々に考えた解法を比べる」前提が崩れるため．ステップ化（#14）の結果も固まり，比較（#16）が安定する
  - `list` も許すのは，#16 で投稿・ステップをまとめて読むため．条件が「その問題で全員が提出したか」だけでドキュメントの中身に依らないので，コレクションの問い合わせでもルールが判定できる
  - テストランナーを足さず `node:test` にしたのは依存を増やさないため．Node 24 は TypeScript の型を取り除いてそのまま実行できる（`server/` と同じ考え）
- 捨てた案とその理由:
  - 作った人が「締め切る」を押す（`closed` 項目を足す）: 契約の項目が増え，作った人が押し忘れると誰も見られない
  - 提出した時点で出し直しを禁止する: 誤って出した人が直せない．他の人の解法はまだ見えないので，そろうまでの出し直しは前提を崩さない
  - 公開の判定を Cloud Functions で行い，公開用のコピーを作る: サーバーの実装が増え，ルールだけで足りる
  - `allSubmitted` に `submittedUids` と `memberUids` の中身の一致まで確かめる: ルールでは集合の比較が書けない．`submittedUids` には参加者が自分の uid しか足せない（重複も不可）ので，件数の一致で足りる
  - ランナーに vitest を足す: 依存が1つ増える
- 承知のうえの弱さ:
  - このルールより前に書いた投稿（`submittedUids` に入っていない人の投稿）は，提出したことにならない．ただし出し直せば，画面が `firstSubmit` で投稿と `submittedUids` を同じバッチで書くので提出扱いになる（テストで確認）．本番のデータは作り直さなくてよい（はじめ「出し直せない」と書いたが誤りで，レビューで指摘された）
  - 参加者が抜ける操作が無いので，提出しない人が1人いると誰も他の人の投稿を見られない（MVP では作った人が声をかける運用）
  - Storage の `clearStorage()` のあとも前のテストのファイルが残ることがあったので，アップロードのテストは毎回違う名前を使う
  - 画面からの提出（ログイン→投稿）はエミュレータで通して確かめられていない（このセッションのブラウザ枠ではログインのポップアップが完了しなかった）．同じ形のバッチはルールのテストで確かめた
- ルールの反映: リポジトリ直下で `npx firebase-tools@15 deploy --only firestore:rules,storage`（レビュー後に人が行う）
