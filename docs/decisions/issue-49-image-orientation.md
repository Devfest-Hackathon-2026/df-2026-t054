# 縦に撮った写真は，上げる前にブラウザで EXIF の向きを画素に反映する（2026-11-08）

<!-- #49: 実装は `web/src/imageOrientation.ts`（呼び出しは `web/src/posts.ts` の `postImages`） -->

- 決めたこと:
  - 画像の投稿を Storage に上げる前に，**JPEG で EXIF の向き（Orientation）が 2〜8（回転あり）のものだけ**，ブラウザで画素を回転した JPEG に作り直して上げる
    - 向きが 1（回転なし）・EXIF が無い・読めない JPEG，PNG・WebP は，今までどおり**元のファイルをそのまま**上げる（画質・大きさが変わらない）
    - 作り直した JPEG には EXIF の向きが残らない（canvas で書き出すため）ので，二重に回ることはない
  - 作り方: `createImageBitmap(file, { imageOrientation: 'from-image' })`（既定値に頼らず明示）→ canvas に描く → `toBlob('image/jpeg')`
  - 向きの読み取りは自前（JPEG の先頭の APP1 から Orientation を探す約 40 行）．**新しい依存は足さない**
  - 大きさ: 長辺が 4096px を超えるときだけ縮める（スマホの標準 4032×3024 は縮めない）．品質は 0.92 → 0.85 → 0.75 の順に試し，1 枚 10MB（`imageMaxBytes`）以内に収まる最初のものを使う
  - 失敗したとき（読み込み・描画のエラー，どの品質でも 10MB を超える）は，**元のファイルをそのまま上げる**（#49 より前と同じ動き．投稿は止めない）
  - 変換は 1 枚ずつ順に行う（12MP の画像を 5 枚同時にメモリへ開かない）
  - Storage のパス・Firestore のデータ構造・`storage.rules` は変えない（共有の契約に触れない）
- 理由:
  - Vertex AI の Gemini は EXIF の向きを反映しない（#9 の測定）．スマホの縦写真はそのまま送ると，どのモデルでも `box2d` が横倒しの座標で返る
  - ブラウザの `<img>` はふつう EXIF の向きを反映して表示する．画素を回転して Gemini が見る画像と画面に出す画像をそろえておけば，将来ステップの枠を画像に重ねたときに位置が合う
  - 回転ありの JPEG だけ作り直すので，多くの写真は元のまま上がり，画質を落とす範囲が小さい
  - サーバー側（`server/`）で回転する案より，依存（sharp など）が要らず，デプロイ（Functions）にも触れない
- 捨てた案とその理由:
  - 全ての JPEG を作り直す: 向きが 1 の写真まで再圧縮して画質が落ちる．直す必要がない
  - `server/` で sharp などで回転する: 新しい依存と Functions のデプロイが要る．ブラウザで足りる
  - EXIF を読むライブラリ（exifr など）を使う: 読むのは Orientation 1 つだけで，約 40 行で足りるので依存を増やさない
  - Gemini へのプロンプトで「画像が回っているかもしれない」と伝える: 座標の向きを AI に補正させることになり，確実さがない
- 承知のうえの弱さ:
  - Storage に残る原本は，回転ありの写真に限り，作り直した JPEG になる（EXIF などのメタデータは残らない）
  - 回転ありの写真は，作り直しの分だけ投稿に少し時間がかかる（合成した 4032×3024 の画像で約 1.1 秒．実機の写真はもう少しかかるかもしれない）
  - 古いブラウザで `createImageBitmap` の `'from-image'` が使えないときは，回転されないまま元のファイルが上がる（#49 より前と同じ）
  - 既に投稿された画像（#49 より前）は直らない．その `box2d` は横倒しのまま
  - JPEG 以外（PNG・WebP）の EXIF の向きは見ない．スマホの標準の撮影は JPEG（iOS は HEIC をファイル選択のときに JPEG へ変える）
