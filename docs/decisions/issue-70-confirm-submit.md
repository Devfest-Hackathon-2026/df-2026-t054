# 投稿（下書き）と提出を分け，本人が AI の分けたステップを見てから「この内容で提出」で確定する（2026-11-08）

011（`011-hide-until-all-submitted.md`）の「投稿＝提出」を変える．「全員が提出したら締め切って公開する」「参加者1人のうちは全員と見なさない」「`allSubmitted` の式」はそのまま．

- 決めたこと:
  - 投稿は下書き．`posts/{uid}` を書いても `submittedUids` には入らない．書けるのは「参加者で，締め切り前で，まだ提出していない」とき（`firebase/firestore.rules`）．下書きのあいだは何度でも出し直せる
  - 提出は別の操作（`web/src/posts.ts` の `submitPost`．`submittedUids` に自分の uid を足すだけ）．ルールの `isSubmit` は，自分の `posts/{uid}` と `steps/{uid}` があり，`steps.status == 'done'` かつ `steps.postCreatedAt == posts.createdAt`（今の投稿と同じ版）であることを確かめる．これで締め切られた問題は全員のステップがそろっている
  - バッチで提出と投稿の書き換えを一緒に送られても通さない．投稿のルールは書いたあとの problem（`getAfter`）で「締め切り前・まだ提出していない」を確かめ，`isSubmit` は書いたあとの投稿（`getAfter`）とステップの版を比べる．はじめは両方とも `get`（バッチの中では書く前の状態）で，提出済みになったうえで投稿だけ新しくなり，ステップがそろわないまま締め切れることを PR #75 のレビューで指摘された（テストで再現してから直した）
  - 提出は締め切り前なら取り消せる（`isWithdraw`．`submittedUids` から自分だけを抜く）．提出したままでは投稿を書き換えられないので，直したいときは取り消してから出し直す．締め切り後は取り消せない
  - 比較（`comparisons`）は，problem の更新で「全員がそろっていなかった → そろった」になったときに作る（`server/src/index.ts` の `problemToComparisons`．`onDocumentUpdated('problems/{problemId}')`）．ステップが done になったときに作る `stepsToComparisons` は，前のルールで締め切られてステップ化があとから終わった問題のために残し，2つは同じ `compareAll` を呼ぶ（作り済みの組は `compare` のトランザクションが飛ばす）
  - 画面: 自分の解法に「下書き」「提出済み」を出す．下書きでは「この内容で提出」（今の投稿のステップが done になるまで押せない）と「出し直す」，提出済みでは「提出を取り消す」を出す（`web/src/SubmitControls.tsx`）．「提出 m 人」に下書きは数えないと書き添えた
  - Storage のルール（`storage.rules`）は変えていない．提出済みの人も締め切り前ならファイルを上げられるが，投稿を書き換えられないので使われない
- 理由:
  - 011 で「提出を別のボタンにしない」と決めたあとに，次の困りごとが分かった: 2人目は自分の投稿がどう分けられたかを見る前に締め切られる／2人目のステップ化が失敗すると締め切り後は出し直せず，比べる画面に進めないまま詰む／招待を配っている途中でも2人がそろうと3人目が参加できなくなる
  - 提出の条件にステップの done と版の一致を入れたのは，「失敗したまま締め切られる」をルールで起こせなくするため．版を見ないと，出し直した直後（前の投稿の done が残っている）に押すと古いステップで提出できてしまう
  - 提出したあと投稿を書き換えられないようにしたのは，提出した版と締め切り時の版がずれると，上の保証（全員のステップがそろっている）が崩れるため
  - 取り消しを許すのは，011 の「誤って出した人が直せる」を保つため．取り消せるのは締め切り前だけで，その間は他の人の解法が見えないので「別々に考えた解法を比べる」前提を崩さない
  - 比較を problem の更新で作るのは，最後の操作が「ステップが done になる」から「提出」に変わったため．提出の時点で全員のステップは done なので，そろった瞬間にまとめて作れる
- 捨てた案とその理由:
  - 作った人が「締め切る」を押す: 011 と同じく，押し忘れると誰も見られない（人間と相談済み．今回はやらない）
  - 提出の取り消しを許さない: 誤って押した人が直せない．ステップを見てから押すので誤りは減るが，ゼロにはならない
  - 提出したあとも投稿の出し直しを許し，出し直したら提出を自動で外す: サーバーかバッチで2つを同時に書く必要があり，ルールが複雑になる．「取り消してから出し直す」で足りる
  - 画面だけでステップの done を確かめ，ルールでは確かめない: 画面を通さずに書くと失敗したまま締め切れてしまう
  - `stepsToComparisons` を消す: 前のルールで締め切られた本番の問題で，あとからステップ化が終わったときに比較が作られなくなる
- 承知のうえの弱さ:
  - 既に `submittedUids` に入っている本番のデータはそのまま（ステップが done か確かめていない）．`submittedUids` に入っていない前の投稿は下書きとして扱われ，ステップが done なら提出できる（テストで確認）
  - 最後の1人が提出した直後，画面はローカルの書き込みで先に「締め切り」と判断し，質問のスレッドを読みにいってルールに拒否されることがある（再読み込みで直る）．011 の「投稿＝提出」のときから同じで，この Issue では直していない
    - → #78 で直した（`issue-78-wait-confirmed-close.md`）
  - 提出しない人が1人いると誰も見られないのは 011 と同じ
- テスト・確認:
  - `firebase/test/rules.test.ts`（48 件．提出と書き換えを同じバッチで送ると拒否．提出の条件: 投稿なし・ステップなし・processing・failed・前の版では拒否，done で同じ版なら成功．取り消し・締め切り後）
  - エミュレータ（Auth・Firestore）で，下書き → ステップ化前は押せない → 提出 → 取り消し → 再提出 → もう1人が提出して締め切り，を画面で確かめた（ステップはサーバーの代わりに手で置いた）．Functions エミュレータで，最後の提出で `problemToComparisons` が動き `comparisons` が作られることを確かめた（Gemini は demo プロジェクトのため呼べず `failed` になる）
